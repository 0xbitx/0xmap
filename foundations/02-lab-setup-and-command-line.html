Lab Setup and the Command Line

Choose a safe lab, read the prompt and learn how commands, help and exit codes fit together.

You do not need a dedicated server to learn Linux. You need a safe environment that you can break, rebuild and snapshot. This part covers the lab choices, the shape of a command line, and the habits that make the terminal predictable.

Choose a lab#

Option Good for Trade-offs
Virtual machine Full Linux install, snapshots, networking Uses RAM and disk
WSL2 on Windows Fast access to a Linux userland Some kernel and service differences
Cloud instance Remote access and realistic networking Costs money, needs careful scope
Live USB Hardware testing and recovery Changes are lost unless persisted
Container Disposable command practice Not a full init or kernel environment

For this handbook, a virtual machine is the best default. Install a Debian or Ubuntu server image, give it at least two CPU cores and 4 GB of RAM, and take a snapshot before you change anything important.

If you use a container, remember that it shares the host kernel. Container root is not automatically host root, but a misconfigured container can still expose the host. Keep the lab isolated.

Use a container as a disposable lab#

A container is the fastest way to get a Linux userland on Windows, macOS or Linux. Install Docker Desktop or Docker Engine, then start an Ubuntu container:

bash
mkdir -p "$HOME/linux-lab"
docker run --rm -it \
  --name linux-lab \
  --hostname linux-lab \
  --cpus 2 \
  --memory 4g \
  -v "$HOME/linux-lab:/data" \
  ubuntu:24.04 bash

This starts an interactive container with a stable name, a hostname, two CPU cores, 4 GB of memory and a bind mount for files you want to keep. The --rm flag deletes the container when you exit. The host directory survives.

On Windows, run the command from WSL2 or use a path that Docker Desktop is allowed to share.

Flag Effect
--rm Delete the container when it exits
-it Attach an interactive terminal
--name linux-lab Give the container a stable name
--hostname linux-lab Set the hostname inside the container
--cpus 2 Limit the container to two CPU cores
--memory 4g Limit the container to 4 GB of memory
-v "$HOME/linux-lab:/data" Mount a host directory at /data
-p 127.0.0.1:8080:80 Publish a container port on loopback only
--env TZ=UTC Set an environment variable
ubuntu:24.04 bash Use this image and run Bash

Inspect and manage the lab:

bash
docker ps
docker ps -a
docker start linux-lab
docker attach linux-lab
docker exec -it linux-lab bash
docker stop linux-lab
docker rm linux-lab
docker system df
docker system prune

With --rm, there is no stopped container to restart after you exit. Remove --rm when you want a persistent container that you can stop and start later. docker exec is often safer than docker attach because it starts a second shell and does not disturb the container's main process.

Never mount /var/run/docker.sock into a lab container. The Docker socket is the control plane for the host daemon. A container that can reach it can start privileged containers, mount host paths and usually take over the host. Avoid --privileged, --pid=host, --network=host and bind mounts of /, /etc, /var or your entire home directory. Publish ports on 127.0.0.1 unless you intentionally want other machines to connect.

A container shares the host kernel and usually does not run a full init system. Use a virtual machine for kernel modules, firewalls, boot troubleshooting and systemd service exercises. Use the container for command practice, file work and disposable experiments.

Know your prompt#

A typical prompt looks like this:

text
alex@lab:~$

It usually contains:

  • alex: the current user.
  • lab: the hostname.
  • ~: the current directory, where ~ means your home directory.
  • $: a normal user prompt. A # usually means root.

The prompt is generated by the shell. You can change it later, but for now read it as a status line: who you are, where you are and how much privilege you have.

The anatomy of a command#

Most commands follow this shape:

text
command [options] [arguments]

For example:

bash
ls -la /var/log
  • ls is the command.
  • -la combines two short options: -l for a long listing and -a to include hidden files.
  • /var/log is the argument, in this case the directory to list.

Long options often use two hyphens:

bash
ls --all --human-readable /var/log

Options change behavior. Arguments tell the command what to act on. Read the manual when the difference is unclear.

Get help without guessing#

Linux ships with documentation. Use it before copying random commands from the internet.

bash
man ls
ls --help
apropos "list files"
info coreutils

man opens the manual page in a pager. Use Up, Down, PageUp, PageDown, / to search and q to quit. The synopsis at the top shows the accepted options. The description explains each one. The examples at the bottom are often the fastest way to learn.

--help is usually shorter and works even when man pages are not installed. apropos searches manual page descriptions. If it returns nothing, the manual database may need to be rebuilt with mandb.

Some systems include tldr, a community-maintained collection of practical examples. It is useful, but it is not a substitute for the real manual.

Exit status and command chaining#

Every command returns an exit status. 0 means success. A non-zero value means failure, and the meaning depends on the program.

bash
ls /etc/passwd
echo "$?"
ls /does-not-exist
echo "$?"

The special variable $? holds the status of the previous command. You can chain commands based on that status:

bash
mkdir -p /tmp/lab && cd /tmp/lab

&& runs the second command only if the first succeeds. || runs the second command only if the first fails. A semicolon runs both regardless.

bash
grep -q root /etc/passwd && echo "root entry found"
grep -q missing /etc/passwd || echo "entry not found"

This is the beginning of shell logic. Later you will use the same idea in scripts.

Quoting and expansion#

The shell expands certain characters before a command runs. The three common quoting forms behave differently:

Form Behavior Example
'single' Literal text, no expansion echo '$HOME'
"double" Expands variables and command substitution echo "$HOME"
backslash Escapes the next character echo \$HOME

Use double quotes by default for variables. Use single quotes when you want the exact text. Use backslash when you need one special character to be literal.

Command substitution runs a command and inserts its output:

bash
today=$(date +%F)
printf 'Today is %s\n' "$today"

The $(...) form is easier to read and nest than backticks.

Redirection and pipes#

Programs read from standard input and write to standard output and standard error. The shell can redirect those streams.

Operator Meaning
> Write standard output to a file, replacing it
>> Append standard output to a file
2> Write standard error to a file
2>&1 Send standard error to the same place as standard output
< Read standard input from a file
| Send standard output to another command

Examples:

bash
ls -la /etc > /tmp/etc-list.txt
grep root /etc/passwd > /tmp/root-entry.txt 2> /tmp/grep-errors.txt
printf 'one\ntwo\nthree\n' | wc -l

A pipe connects commands into a small data-processing pipeline. This is one of the most important ideas in the shell. You will use it constantly.

Terminal habits#

  • Use Tab to complete paths and command names. It reduces typos.
  • Use Ctrl+R to search your command history.
  • Use Ctrl+C to interrupt the foreground command.
  • Use Ctrl+D to send end-of-file or exit an interactive shell.
  • Use Ctrl+L to clear the screen without losing your place.
  • Use history to review previous commands.
  • Use !! to repeat the last command, and !$ for its last argument.

Be careful with !! and sudo. Read the command before you run it again.

Manual sections and command discovery#

Manual pages are organized into numbered sections. The same name can appear in more than one section with different meanings.

Section Contents Example
1 User commands man 1 ls
2 System calls man 2 open
3 Library functions man 3 printf
4 Device files man 4 tty
5 File formats and configuration man 5 passwd
7 Miscellaneous concepts man 7 signal
8 System administration commands man 8 mount

If you are not sure where a command lives, ask the system:

bash
type -a ls
command -v ls
which ls
whereis ls
whatis ls

type -a reports every definition the shell knows about, including aliases and functions. command -v prints the path or builtin name the shell would use. which searches PATH but may not see functions or builtins. whereis finds binaries, source and manual pages. whatis prints the one-line manual description.

Manual pages can be searched by keyword:

bash
apropos 'copy files'
man -k 'copy files'

If apropos returns nothing, the manual database may be missing. Rebuild it with sudo mandb on Debian or Ubuntu.

Startup files and environment#

The shell reads configuration files when it starts. The exact files depend on the shell and on whether the session is a login shell, an interactive shell or a script.

For Bash, the common files are:

File Typical use
/etc/profile System-wide login shell settings
/etc/bash.bashrc System-wide interactive Bash settings on Debian and Ubuntu
~/.profile Per-user login shell settings
~/.bash_profile Per-user login shell settings, if present
~/.bash_login Alternative login file, read if .bash_profile is absent
~/.bashrc Per-user interactive Bash settings

Bash reads only the first of ~/.bash_profile, ~/.bash_login or ~/.profile that exists for a login shell. Interactive non-login shells usually read ~/.bashrc. Scripts normally read neither, unless they source a file explicitly.

This is why environment changes can appear inconsistent. A variable exported in ~/.bashrc may not exist in a systemd service, a cron job or a non-interactive SSH command. Put system-wide environment settings in the right place for the service manager, not in a shell startup file.

Inspect the environment:

bash
env
printenv
printenv PATH
set
export MY_LAB=foundations
printenv MY_LAB

env and printenv show exported variables. set also shows shell variables and functions. export marks a variable for child processes. A variable can exist in your shell and still be invisible to a program if it was never exported.

Common variables worth understanding:

Variable Meaning
HOME Your home directory
USER Your username
PATH Search order for commands
PWD Current working directory
OLDPWD Previous working directory
SHELL Configured login shell
LANG, LC_* Locale and character handling
TERM Terminal type
EDITOR, VISUAL Preferred text editor
TMPDIR Preferred temporary directory

Aliases, functions and history#

An alias is a short name for a command line. It is expanded by the interactive shell before the command runs.

bash
alias ll='ls -la'
alias
unalias ll

Aliases are convenient but fragile. They are not available to scripts by default, and they do not accept arguments in the same way as a function. For anything more complex, use a function.

bash
mkcd() {
    mkdir -p -- "$1" && cd -- "$1"
}
mkcd ~/linux-foundations/lab02

A function runs in the current shell, so cd inside it changes your directory. That is useful for workflow helpers. Put functions in ~/.bashrc or a separate file that you source.

History is a working memory aid:

bash
history
history 20
history | grep ssh
!! 
!$ 
!42

!! repeats the previous command. !$ inserts the last argument of the previous command. !42 runs history entry 42. Be careful with sudo !!. Read the command before repeating it with elevated privilege.

Useful history settings in ~/.bashrc:

bash
HISTSIZE=5000
HISTFILESIZE=20000
HISTCONTROL=ignoreboth
shopt -s histappend

ignoreboth avoids storing duplicate lines and lines that begin with a space. histappend appends to the history file instead of overwriting it when a shell exits.

How the shell parses a command#

The shell performs several expansions before a program starts. A simplified order is:

  1. Split the input into tokens using quoting rules.
  2. Expand aliases in interactive shells.
  3. Expand braces, such as {a,b}.
  4. Expand tilde, such as ~ and ~user.
  5. Expand parameters and variables, such as $HOME.
  6. Perform command substitution, such as $(date).
  7. Perform arithmetic expansion, such as $((2 + 2)).
  8. Split unquoted results into words.
  9. Expand glob patterns, such as *.conf.
  10. Remove quote characters.
  11. Run the command with the resulting arguments.

The order explains many surprises. A variable containing spaces becomes several arguments if you leave it unquoted. A glob inside quotes stays literal. A command substitution that outputs a newline can change the argument count.

bash
name='two words'
printf '[%s]\n' $name
printf '[%s]\n' "$name"

The first printf receives two arguments. The second receives one. This is one of the most important quoting lessons in shell work.

More redirection#

The basic redirection operators are only the start. The shell can also feed a command from a here document or a here string.

bash
cat <<'EOF'
line one
line two
EOF

grep root <<< 'root:x:0:0:root:/root:/bin/bash'

A quoted here document delimiter, such as 'EOF', prevents variable expansion. An unquoted delimiter allows it. Here strings are convenient for a single line of input.

Discard output or errors:

bash
command > /dev/null
command 2> /dev/null
command > /dev/null 2>&1

/dev/null is a device that discards everything written to it. Redirecting both streams is common when a script only cares about the exit status.

Send output to a file and the terminal at the same time:

bash
command | tee output.txt
command | tee -a output.txt

Append both standard output and standard error to one file:

bash
command >> combined.log 2>&1

Order matters. In > file 2>&1, standard error is pointed at the same place standard output currently points. In 2>&1 > file, standard error still points at the terminal because the order is reversed.

Lab: build a workspace#

Create a small workspace and practice the basic operations:

bash
mkdir -p ~/linux-foundations/lab01
cd ~/linux-foundations/lab01
pwd
printf 'alpha\nbeta\ngamma\n' > words.txt
ls -la
wc -l words.txt
cat words.txt
grep beta words.txt

Now test exit status:

bash
grep alpha words.txt
echo "$?"
grep missing words.txt
echo "$?"

Finally, read the manual for a command you use every day:

bash
man ls

Search for the -h option and the -t option. Write one sentence explaining what each does.

Common mistakes#

  • Running a command as root before reading what it does.
  • Forgetting that > overwrites a file.
  • Using rm -rf with a variable that turned out to be empty.
  • Assuming --help and the man page always say the same thing.
  • Copying a command with curly quotes or hidden Unicode characters.

Checkpoint#

You should now be able to:

  • Start a safe Linux lab and take a snapshot.
  • Read a shell prompt.
  • Break a command into command, options and arguments.
  • Find help with man and --help.
  • Chain commands with && and ||.
  • Redirect output and build a simple pipeline.
