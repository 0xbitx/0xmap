Section 05 / Defense and workflow

Automating Linux Privilege Escalation Checks

Use LinPEAS, LSE and custom checks to reproduce a repeatable enumeration pass.

Objective#

Learn how to automate privilege escalation checks on Linux using scripts and well-known tools like linpeas, lse, and custom Bash one-liners. Focus on collecting misconfigurations efficiently and safely during post-exploitation or pentesting.

1. Why Automate Privilege Escalation?#

Manual enumeration is time-consuming. Automated scripts speed up information gathering by listing misconfigurations, weak permissions, and exploitable binaries.
However, always review script outputs manually before attempting exploitation.

2. Key Tools#

LinPEAS#

LinPEAS is a popular script for privilege escalation checks.

bash
wget https://github.com/carlospolop/PEASS-ng/releases/latest/download/linpeas.sh
chmod +x linpeas.sh
./linpeas.sh

It checks for:

  • SUID/SGID binaries
  • Writable /etc/passwd
  • Crontabs and PATH hijacks
  • Capabilities, Docker, NFS, and kernel exploits

Linux Smart Enumeration (LSE)#

A modular and cleaner enumeration tool:

bash
wget https://github.com/diego-treitos/linux-smart-enumeration/releases/latest/download/lse.sh
chmod +x lse.sh
./lse.sh -l2

LSE provides detailed but safe enumeration without exploit attempts.

3. Writing Your Own Automation Script#

You can build your own script combining simple commands:

bash
#!/bin/bash
echo "[*] User info:"
id
echo "[*] Sudo permissions:"
sudo -l
echo "[*] SUID binaries:"
find / -perm -4000 2>/dev/null
echo "[*] Writable /etc files:"
find /etc -writable 2>/dev/null

Save as enum.sh and run with:

bash
bash enum.sh > results.txt

4. Useful One-Liners#

bash
find / -type f -perm -4000 2>/dev/null       # Find SUID binaries
sudo -l                                      # Check sudo permissions
cat /etc/passwd | grep sh$                   # Users with shell access
getcap -r / 2>/dev/null                      # List files with capabilities
ls -la /root                                 # Try if root directory is accessible

5. Privilege Escalation Targets#

  • Misconfigured sudo rules (e.g., NOPASSWD)
  • Writable scripts executed as root (cron/systemd)
  • SUID binaries allowing command execution
  • Files with dangerous capabilities (setcap cap_setuid+ep)
  • Weak environment variable paths

Advanced: What scanners miss#

Automated enumerators are good at finding known patterns and bad at understanding context. Recent privilege escalation bugs often live in trusted update or helper paths that scanners do not model.

Recent examples:

  • CVE-2025-32463: sudo before 1.9.17p1 could load /etc/nsswitch.conf from a user-controlled directory when --chroot was used, leading to root.
  • CVE-2025-32462: a sudoers host mismatch could let listed users run commands on unintended machines.
  • CVE-2024-48990 and CVE-2024-11003: needrestart before 3.8 could execute code as root through PYTHONPATH or unsafe library input.
  • CVE-2021-4034 (PwnKit) in polkit's pkexec is still found on unpatched images.
  • CVE-2023-4911 (Looney Tunables) in the glibc dynamic loader affected many distributions.

Check versions and patch state:

bash
sudo -V | head -n 1
dpkg-query -W sudo needrestart policykit-1 libc6 2>/dev/null
rpm -q sudo needrestart polkit glibc 2>/dev/null

Manual validation:

bash
sudo -l
getcap -r / 2>/dev/null
capsh --print
find / -xdev -perm -4000 -type f 2>/dev/null
systemd-analyze security --no-pager

Use pspy to watch short-lived root processes and timers that a one-shot scan misses:

bash
./pspy64 -pf -i 1000

Workflow:

  1. Enumerate versions and patch levels, not just binaries.
  2. Map each finding to a concrete precondition check.
  3. Validate with a non-destructive proof in a snapshot.
  4. Record false positives and why they are not exploitable.
  5. Patch or remove the helper, then re-test.

Do not run unknown exploit binaries on a host you do not own. A scanner finding is a hypothesis, not a compromise.

Privilege escalation field checklist#

Use scanner output as an index, not as a conclusion. The table below covers the surfaces that most often turn a low-privileged shell into root, including areas that are easy to miss in a one-shot scan.

Surface What to check Starting point
sudo NOPASSWD, ALL, wildcard rules, shell escapes, env_keep sudo -l
SUID and SGID writable binaries, unexpected owners, GTFOBins entries find / -xdev \( -perm -4000 -o -perm -2000 \)
Capabilities cap_setuid, cap_setgid, cap_dac_override, cap_sys_admin, cap_sys_ptrace getcap -r /
Scheduled jobs writable scripts, relative commands, wildcard expansion crontab -l, systemctl list-timers --all
Writable system files passwd, shadow, sudoers, PAM, profile, ld.so.preload find /etc -xdev -writable
PATH and environment writable PATH directory, LD_PRELOAD, LD_LIBRARY_PATH, PYTHONPATH, BASH_ENV, EDITOR, PAGER echo "$PATH", env
Services writable unit or binary, root execution, unsafe ExecStart systemctl list-units --type=service
NFS no_root_squash, writable exports, UID/GID mapping showmount -e <host>, cat /etc/exports
Containers docker group, socket mount, privileged mode, host namespaces docker info, capsh --print
Kernel patch level, exposed modules, missing mitigations uname -r, sysctl kernel.kptr_restrict

Two surfaces deserve extra attention. If an NFS export is writable and allows no_root_squash, root on the client can place a SUID binary that executes as root on the server. If the Docker socket or docker group is exposed, treat it as root: a privileged container can mount the host filesystem.

A compact collection pass:

bash
id
sudo -l
sudo -V | head -n 1
getcap -r / 2>/dev/null
capsh --print

find / -xdev -type f \( -perm -4000 -o -perm -2000 \) \
  -printf '%m %u %g %p\n' 2>/dev/null
find /etc -xdev -writable -printf '%m %u %g %p\n' 2>/dev/null
printf '%s\n' "$PATH" | tr ':' '\n'

crontab -l 2>/dev/null
ls -la /etc/cron.* /etc/cron.d 2>/dev/null
systemctl list-timers --all
systemd-analyze security --no-pager
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS

showmount -e 127.0.0.1 2>/dev/null
docker info --format '{{.ServerVersion}} {{.SecurityOptions}}' 2>/dev/null

find / can be slow on large systems. Use -xdev to stay on one filesystem, and start with the directories that matter for the service you are targeting.

Validate the lead#

  • Reproduce the permission or configuration with ls -l, stat, namei -l and systemctl cat.
  • Confirm the privileged context. A writable file is only interesting if root or a privileged service reads or executes it.
  • Check the binary's documented shell escapes on GTFOBins, then test the exact version in a lab.
  • Use a harmless proof, such as creating a marker file. Do not leave a root shell, new account or persistence behind on a client system.
  • Record the exact command, precondition, impact and false positives, then clean up test files and reverse configuration changes.

External field notes#

JoramMalley's Linux privilege escalation notes are a useful topic index for the checks above: Linux-privilege-escalation. The repository is third-party material. Verify its commands and CVE claims against vendor advisories before use, and treat every technique as lab-only unless you have written authorization.

6. Best Practices#

  • Run automated tools with low noise flags to avoid detection.
  • Redirect output to local files for review (tee, >, or 2>/dev/null).
  • Keep your custom script modular - add functions per category (users, services, permissions).
  • Always respect legal & ethical boundaries.

7. Challenge (Lab Task)#

  1. Run linpeas.sh and lse.sh on a lab VM.
  2. Compare results - note what each finds differently.
  3. Add one of your custom checks (like world-writable configs).
  4. Report findings in a simple table format (tool → finding → impact).

Ethics & Safety: Run these tools only on systems you own or are authorized to test. Unauthorized scanning or exploitation is illegal.
