Linux Memory Analysis and Credential Hunting

Inspect procfs and live processes to find credentials and runtime evidence.

6 min read 10 sections 13 code blocks Chapter 29 / 30

Linux memory analysis is an advanced but extremely powerful skill for hackers, red teamers, and incident responders.
Many secrets never touch disk - they live only in memory. Linux memory analysis for credential hunting involves capturing volatile data (RAM) to identify sensitive information like passwords, SSH keys, and session tokens that may not exist on disk.

1. Why Memory Matters#

Sensitive data often found only in RAM:

  • cleartext passwords
  • API tokens
  • database credentials
  • decrypted configuration values
  • session secrets

If you can inspect process memory, you can bypass many traditional security controls.

2. Understanding /proc#

The /proc filesystem exposes live process information.

List processes:

bash
ls /proc

Inspect a specific process:

bash
ls /proc/<pid>

Important files:

  • cmdline → startup command
  • environ → environment variables
  • maps → memory layout
  • mem → raw process memory

3. Credential Hunting via Environment Variables#

Many applications load secrets via environment variables.

bash
cat /proc/<pid>/environ | tr '\0' '\n'

Look for:

  • PASSWORD
  • TOKEN
  • SECRET
  • AWS_
  • DB_

4. Extracting Strings from Process Memory#

If permissions allow:

bash
strings /proc/<pid>/mem | grep -i pass

Inspect mapped regions:

bash
cat /proc/<pid>/maps

Advanced extraction:

bash
dd if=/proc/<pid>/mem bs=1 skip=<start> count=<size>

5. Live Target Discovery#

Check running services:

bash
ps aux | grep mysql
ps aux | grep postgres
ps aux | grep redis

Secrets often appear in:

  • command-line arguments
  • memory buffers
  • config loaders

6. Attaching to Processes (gdb-lite)#

If allowed:

bash
gdb -p <pid>

Search memory:

bash
find &__data_start__, +9999999, "password"

Detach safely:

text
detach
quit

7. Privilege Escalation Angle#

Potential escalation paths:

  • reading root-owned process memory
  • attaching to privileged daemons
  • leaking secrets from SUID helpers

8. Restrictions & Protections#

  • ptrace may be restricted (ptrace_scope)
  • /proc/<pid>/mem often requires same UID or root
  • hardened kernels reduce memory visibility

Advanced: Modern process memory and kernel keyring#

Linux does not have a single credential store. Secrets live in environment variables, command lines, configuration files, agent sockets, the kernel keyring and process memory. Modern access often goes through ptrace, process_vm_readv, memfd or BPF rather than /proc/<pid>/mem alone.

Check restrictions:

bash
cat /proc/sys/kernel/yama/ptrace_scope
cat /proc/sys/kernel/perf_event_paranoid
cat /proc/sys/kernel/unprivileged_bpf_disabled
cat /proc/<pid>/maps

Memory access examples, lab only:

bash
gcore -o /tmp/core <pid>
grep -aE 'password|token|secret|API_KEY' /proc/<pid>/environ
keyctl show

Modern primitives:

  • process_vm_readv reads another process's memory without a full ptrace stop, subject to the same Yama policy.
  • memfd_create creates an anonymous file; combined with fexecve it supports fileless execution and is a common detection target.
  • pidfd provides race-free process handles and is increasingly used by supervisors and security tools.
  • perf_event_open and BPF maps can expose kernel and user memory events; both are privileged and audited.
  • The kernel keyring (keyctl) stores keys for services and users; inspect permissions before assuming a key is readable.

Credential targets:

  • systemd credentials and environment files.
  • SSH agent sockets and ~/.ssh keys.
  • Cloud instance metadata tokens, especially IMDSv1.
  • Container secrets mounted as files.
  • Password manager and GPG agent caches.

Defenses:

bash
sudo sysctl -w kernel.yama.ptrace_scope=2
sudo sysctl -w kernel.perf_event_paranoid=3
sudo sysctl -w kernel.unprivileged_bpf_disabled=2

Also use hidepid=2 on /proc, restrict CAP_SYS_PTRACE, and audit process_vm_readv, ptrace, memfd_create and bpf syscalls. Validate that monitoring and debugging tools still work before enforcing these settings.

9. Defender Awareness#

Blue teams should:

  • avoid secrets in env vars
  • restrict ptrace usage
  • monitor /proc access
  • enforce memory-safe coding practices
